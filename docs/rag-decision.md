# RAG 决策评估

## 结论

**当前不引入 RAG**。本仓库定位为提示词工程库与校验工具，没有知识库、检索或向量存储的需求信号；提前引入 Chunking、Embedding、向量库会增加维护成本，且无法验证收益。

## 决策依据

1. 流水线的输入是单次用户需求与上游 Agent 输出，不是大规模文档检索；
2. 现有提示词已通过“上下文瘦身、输入上限、数据边界”控制质量，没有“上下文不足”的明确瓶颈；
3. 引入 RAG 需要配套的文档源、分块策略、检索评测与成本控制，目前均无落地场景；
4. 按“不为没出现的问题设计”原则，保持零运行时依赖。

## 触发条件（满足其一再评估）

- 需要让 Agent 基于项目既有代码库/文档回答或生成，且内容无法全部放入上下文；
- 出现“不知道项目约定”“引用了不存在的 API”等系统性失败，且确认是信息缺失而非提示词问题；
- 集成方明确提出知识库问答或代码检索需求。

## 如果未来需要：最小方案

1. 先做数据准备：确定文档源、清洗规则与更新频率；
2. 最小分块：按标题/函数/段落切分，记录 metadata（来源、路径、更新时间）；
3. 检索：先用关键词/BM25 验证召回是否够用，再评估 Embedding 与向量库；
4. 接入点：在 Planner 阶段前注入“项目约定/参考资料”作为只读数据，保持数据与指令分离；
5. 评测：沿用 `docs/evaluation.md` 的 golden 场景，增加“知识引用正确性”检查项。

## 不做什么

- 不预先引入向量数据库、Embedding SDK 或检索框架；
- 不把 RAG 能力做成插件式抽象——等真实需求出现后再设计，避免过度工程。
